# 电商运营助手接口契约 v1.0

版本：1.0.0（接口设计基线，待项目评审后冻结）  
日期：2026-10-23  
来源：用户提供的《电商运营助手.md》2.6节及本次讨论。原始文档不作修改。

本交付只定义HTTP接口和可观察业务行为，不包含后端实现、数据库DDL或Docker Compose，也不表示接口已上线。接口路径、字段及状态以同目录OpenAPI文件为机器可读定义，本文补充不能仅靠JSON Schema表达的业务约束；两者共同构成契约，冲突须修订后再实现，不由实现端自行选择。

## 1. 范围、来源与设计决定

已确定：单团队、单店铺；React前端；FastAPI + SQLAlchemy + PostgreSQL；MinIO保存图片、视频及导入文件；CentOS 7为固定部署环境。部署兼容性验证属于后续交付，不改变本契约的外部行为。

原文2.6.10中每个HTTP方法与路径均保留；本契约在路径表中标记“原文”。其他路径标记“补充”，用于补齐读取、轮次、SKU/库存、标题、文件、导入、编辑与配置操作。原文规定了异步图片/视频；本设计进一步把六处AI判断均纳入异步任务。单店铺保留stores集合接口，结果最多一条。

以下是本契约采用的设计默认值，属于本次补充设计，不应误认为原文已明确规定：

- 每个商品同时最多一个active运营轮次；后续轮次通过上一轮复盘和采纳动作关联。
- 一个轮次同一方案类型最多一个selected；主图、视频脚本、标题分别至少生成3份候选。
- 启用商品须至少一个启用SKU和一张已验证原图；诊断前先启用商品。
- 登录令牌有效2小时，不提供refresh接口，过期重新登录。
- 金额固定CNY、时区Asia/Shanghai；经营数据使用自然日粒度，收入/花费解释为ROAS，原roi字段暂返回null。
- 业务POST/PATCH使用幂等键；编辑使用乐观锁；公开跳转及文件下载有明确例外。
- 密钥只接受环境变量引用，不通过API提交真实模型密钥。
- 第一版不提供硬删除API，以停用、归档、取消或作废保留引用链和审计。

图片/视频供应商和真实接入程度尚未确定：契约同时支持real与demo，通过模型配置显式选择。未配置能力必须明确报错，不能静默用演示结果替代真实生成。不同供应商适配在后端内部实现，不让前端提交任意供应商请求体。

## 2. 通用HTTP约定

### 2.1 路径、编码与类型

- 所有路径完整前缀为`/api/v1`；OpenAPI servers已含此前缀，paths不重复添加。
- JSON使用UTF-8、snake_case；请求对象拒绝未声明字段，返回422，避免把表单残留、密钥或客户端计算字段带入。
- 主键为UUID字符串；服务端生成。所有归属由服务端校验，product_id不允许靠修改请求体改变。
- 日期为`YYYY-MM-DD`；时间为带时区的RFC 3339，响应统一UTC `Z`。经营日期与日统计按Asia/Shanghai解释，日期区间两端包含。
- 金额为两位小数非负字符串，例如`"199.00"`，服务端Decimal计算。计数为整数，经营计数最大9007199254740991；比率为最多6位小数的十进制字符串，`"0.12"`表示12%。分母为0时比率返回null。
- POST省略的可选数组默认[]、可空字段默认null；状态默认值见Schema。PATCH省略表示不变，null仅允许在显式可空字段中清空，空对象返回422。CreativePlanPatch为特例：提交完整的可编辑方案，以校验不同内容类型。
- 集合默认`page=1&page_size=20`，page_size上限100，默认updated_at倒序、id倒序；无updated_at用created_at倒序、id倒序。事件按sequence升序。未知筛选字段返回422，不提供任意SQL式排序参数。未命中集合返回200及空数组，页码超过末页仍为空数组。

### 2.2 响应

普通成功：
```json
{"data":{"id":"11111111-1111-4111-8111-111111111111","version":1},"meta":{"request_id":"00000000-0000-4000-8000-000000000001"}}
```
上例只示意外层包裹，data的完整必填字段以对应Schema为准。

列表成功：
```json
{"data":[],"meta":{"request_id":"00000000-0000-4000-8000-000000000001","page":1,"page_size":20,"total":0,"total_pages":0}}
```

失败（不返回伪200）：
```json
{"error":{"code":"VERSION_CONFLICT","message":"资源已更新，请读取最新版本后提交","details":[{"field":"If-Match","row_number":null,"code":"STALE_VERSION","message":"当前版本为4"}],"retryable":false},"request_id":"00000000-0000-4000-8000-000000000001"}
```

200读取/更新/确定性操作；201同步创建；202已受理任务而非业务已完成。302推广跳转无JSON包装；CSV模板直接返回文件。JSON响应带X-Request-ID；服务端生成request_id，不信任外部任意输入。

### 2.3 登录与权限

除POST /auth/login与GET /r/{tracking_code}外均要求`Authorization: Bearer <access_token>`。公开跳转的HEAD行为与GET相同但不记点击；HEAD无响应体。退出后令牌立即失效。用户禁用或角色/密码变化时撤销该用户全部会话。

角色：admin（管理员）、operator（运营）、viewer（查看）。查看人员只有读权限；管理员和运营可操作商品及运营流程；用户、店铺配置、模型与系统配置、维护任务只允许管理员。公开点击记录、调度器及Worker的受控写入由后端系统身份承担，不构成匿名业务写接口。

专项权限由后端映射：`users:manage`仅admin；`ads:confirm`与`experiments:update`为admin/operator；`assets:review`为admin/operator；`maintenance:run`与`demo:initialize`仅admin。管理员/运营均可确认本人创建的建议，第一版不额外引入双人审批。OpenAPI每个操作的x-roles为必须执行的角色集合，x-permission为该操作的权限标识；后端按整份操作表建立角色到权限映射，不能仅靠`:read`/`:write`后缀推断角色。全局Bearer登录成功不代表拥有某条操作权限。

检查顺序：身份→角色/专项权限→路径资源归属→幂等记录→版本/字段/状态与事务。未知或跨商品资源统一404；角色不足403。日志及响应不得包含密码散列、模型密钥、平台token/cookie或内部供应商凭据。

### 2.4 幂等与并发

所有业务POST/PATCH必须发送`Idempotency-Key: <UUID>`；认证接口不要求。作用域为当前用户+HTTP方法+规范路径，记录24小时。指纹含规范JSON字段值；multipart含文件SHA256、文件名、类型、用途和product_id。关联资源路径属于指纹作用域。If-Match属于前置条件，不影响同一次成功请求的重放。

- 同键同请求：鉴权通过后返回原成功响应、原HTTP状态及原业务结果，即便当前版本已前进；meta.request_id可以为本次请求ID。异步请求重放不创建新任务。
- 同键不同请求：409 IDEMPOTENCY_KEY_REUSED。同键首个请求仍在处理：409 IDEMPOTENCY_IN_PROGRESS，details给重试提示。
- 幂等占位与业务写入必须保持一致性，成功的2xx结果保存；4xx/5xx不作为成功缓存，同指纹可在修正外部条件后重试，但改变请求体必须换键。
- 缺少Idempotency-Key返回400 IDEMPOTENCY_KEY_REQUIRED，格式非法返回400 INVALID_IDEMPOTENCY_KEY。
- 单资源修改读取version后发送`If-Match: "3"`；GET单资源返回ETag。缺少428、格式非法400、版本不符412。version每次有效修改+1，检查和写入同事务执行。
- 批量素材审核不使用单一If-Match，而是每项expected_version；任一冲突412且整批回滚。库存调整的If-Match引用Inventory，响应ETag也引用调整后Inventory。
- 所有状态操作同时受幂等和状态机约束，避免双击确认、重复加库存或重复导入。后端不能只依赖前端禁用按钮。

## 3. 业务闭环、版本和状态

### 3.1 主线与版本引用

建店→建商品/SKU/库存/原图→竞品→启用商品→创建轮次→诊断→人工选定诊断→主图/脚本/标题→选定方案→异步生成→人工审核→链接与投放建议→人工确认→实验草案→人工确认实验→平台人工执行→回填日数据→复盘→完成本轮→从复盘创建下一轮。

所有诊断、方案、素材、建议、实验、经营记录和复盘均关联product_id；本轮生成与实验记录还关联round_id。文件可先上传后绑定，import文件暂不要求product_id。商品基础数据为长期档案，运营输出不是商品表字段。

ResourceRef `{id,version}`表示不可变修订，禁止服务端自动替换为最新版本。诊断/方案/建议/复盘每次内容、状态、确认变化都增加version并保存完整修订；修订接口可读取历史。生成时固化商品/竞品快照、模型配置非敏感版本、提示词版本和引用版本。确认记录与下游实验都绑定批准版本。审核状态和库存等实时约束，在确认或执行入口还必须重新校验。

已完成/取消轮次只读，可读取、汇总和下载，但不得产生新业务写入、重试或改数据。进入首个创意任务后本轮诊断锁定；需要改变诊断时，应取消或完成本轮再建新轮次。复盘动作被采纳时保存来源报告版本和action_id，不能只复制一段文字。

### 3.2 状态规则

| 对象 | 状态与合法迁移 | 额外规则 |
|---|---|---|
| 商品 | draft→active/inactive；active→inactive；inactive→active/draft | 启用检查SKU与原图；停用后禁止新生成和启动实验，允许active历史轮次补录/复盘 |
| 轮次 | active→completed/cancelled | completed须有复盘、全部实验finished/cancelled且任务终态；cancelled前先取消未结束实验/任务 |
| 方案 | draft↔selected；draft/selected→archived；archived→draft | 同轮次同类型最多一个selected；修改内容强制draft；已引用修订不变 |
| 素材审核 | pending→approved/rejected；rejected→pending；approved→rejected | 驳回须原因；被confirmed/running实验引用时不得撤回通过状态 |
| 任务 | pending→running/cancelled/timeout；running→succeeded/failed/cancelled/timeout | failed/timeout可依策略回pending；终态成功/取消不允许重试 |
| 投放建议 | pending→confirmed/rejected；编辑生成新pending修订 | 不能直接rejected→confirmed；确认只对指定版本生效 |
| 实验 | draft→confirmed/cancelled；confirmed→running/cancelled；running→finished/cancelled | draft可编辑计划；确认后预算/人群/素材/链接冻结，改方案应取消并新建草案 |
| 导入 | validating→preview_ready/failed；preview_ready→committing/expired；committing→succeeded/partially_succeeded/failed | 预览不写业务；提交再次校验；终态不重复提交 |

stage为派生的页面引导进度，不是另一个强制状态机：分析生成前draft、诊断任务diagnosing、选择诊断后creative、媒体任务generating、待审核reviewing、建议/草案planning、实验运行executing、数据/复盘analyzing；存在多种活动时显示当前最早未满足的主线环节。completed/cancelled优先。前端应依据具体对象状态启用按钮，而非仅靠stage。

## 4. Agent边界与异步任务

| 六处模型判断 | Agent | 作业类型 | 输出资源 |
|---|---|---|---|
| 诊断 | analysis | diagnosis | Diagnosis |
| 主图方案 | creative | main_image_plan | 至少3个MainImagePlan |
| 视频脚本 | creative | video_script | 至少3个VideoScriptPlan |
| 标题方案 | creative | title_plan | 至少3个TitlePlan |
| 投放 | strategy | ad_recommendation | AdRecommendation |
| 复盘 | analysis | review_report | ReviewReport |

图片/视频生成是creative职责下调用专用媒体服务，作业image/video；不是用语言模型返回一段文字冒充媒体。库存建议、推广链接建议、指标计算、实验草案展开、权限和预算校验使用确定性代码，不增加模型判断点。

生成接口202返回JobAccepted，包含job、poll_url、events_url、poll_after_seconds；响应Location等于poll_url。商品任务使用商品任务详情/事件路径；维护和演示任务使用workspace/jobs路径。poll_url以实际返回为准，不让前端从job_kind猜地址。

JobAccepted中的job可以已经是succeeded（例如极速演示任务），202只表示此次异步受理协议。前端按建议间隔轮询，终态停止；读取任务成功后根据result_resources取业务详情。结果引用不能出现未落库资源。诊断/建议/复盘各1个结果；创意候选为count个；图片为count个，视频1个。维护作业无业务资源时result_resources=[]，处理数量写入事件摘要。

任务attempts为已开始的执行次数，入队为0，每次开始+1；max_attempts入队固化，默认3，范围1–5，不能通过重试接口提高。执行进度0–100只是展示，成功为100，不承诺供应商精确进度。默认总执行超时1800秒，以入队配置固化；排队等待超过24小时也标记timeout。运行租约与心跳使崩溃任务可被识别，旧Worker不能在失去租约后发布结果。

自动重试仅限明确安全的暂时失败，退避30秒、120秒，写retry_scheduled事件。不能盲目重发可能已提交、会计费的图片/视频请求；需持久保存供应商请求标识并查询结果。无法确认是否受理时使用PROVIDER_SUBMISSION_UNKNOWN，人工重试返回409 RECONCILIATION_REQUIRED，待后台核对后再决定恢复或新建。异步执行错误通常体现在任务error_code/error_message，而不是让最初202变成错误。

同一job重试使用同一业务输入快照；如果要改内容或模型，应创建新任务、新幂等键。生成输出以(job_id,输出序号)去重，第三方已生成但MinIO上传/数据库登记失败时优先恢复保存，不重新生成计费。多图任务只有全部输出校验和持久化后才succeeded并发布素材；部分失败暂存结果不对素材库可用，同步/重试不能重复登记。

取消接口202：pending可立即cancelled；running先cancellation_requested=true，Worker尽快结束。第三方不能取消时不保证停止计费；取消/超时后的迟到结果记late_result_ignored并隔离，不恢复任务、不生成可用素材。成功落库事务与取消请求按版本/任务锁互斥，已成功返回409 JOB_TERMINAL。

公开链接解析保留原文的“创建→run”两步：创建201为pending+awaiting_dispatch，run才入队。任务完成后结果为候选，由用户创建/更新竞品采纳。监控生成快照，不覆盖人工资料。所有出站URL及重定向均校验，防止SSRF；不绕过登录、验证码或平台风控。

AI必须先校验结构、预算及引用，再保存业务结果；模型结果格式不合法为AI_OUTPUT_INVALID。失败不能写入残缺诊断或建议。生成时的原始结果内部保留并脱敏，不通过普通业务API返回供应商原始响应。

## 5. 素材、MinIO与演示隔离

上传→FileObject→业务引用file_id；人工素材再通过POST assets登记为Asset。生成素材由Worker完成这两步。MinIO桶私有，前端不接收存储密钥或任意对象写权限；本版上传经FastAPI转存，后续可扩展直传，不改变现有file_id引用。

product_image/reference/media要求product_id，文件只能被同商品引用；import用于导入批次，可暂不挂商品。图片20MiB、视频500MiB、导入10MiB，系统设置只能下调硬上限；图片JPEG/PNG/WebP，视频MP4，导入UTF-8 CSV/XLSX。校验真实文件类型，禁止SVG/可执行/宏文件/解压炸弹；失败不创建available文件。错误用413、415或422 FILE_VALIDATION_FAILED。

GET access-url是登录后授权读取，返回300秒签名地址，响应本身应no-store。所有引用保存file_id，对象路径由后端管理；不把会过期的签名URL持久化到商品、素材或报告。

审核通过不代表模型判断商品真实，审核人员需检查事实、画面和文案；审核行为由后端记录人、时间、意见。文件内容不原地替换；parent_asset_id生成新的素材版本，旧实验引用保持不变。

execution_mode=demo用于演示模型/媒体/实验；真实模式不得静默降级。所有AI结果有provenance.execution_mode，任务与素材/实验也有execution_mode。real实验拒绝demo素材；同一复盘不混合demo与real实验数据。演示初始化仅允许空业务环境，避免把演示数据混入已有单店铺。

## 6. 投放建议、确认与实验

策略输入的预算上限、每日上限、天数由人填写。总预算与每日上限必须>0，建议total_amount<=budget_cap，daily_cap<=请求daily_cap且不大于总预算，duration_days不得超过请求duration_days；各allocations金额和等于total_amount，total_amount<=daily_cap×duration_days。预算分配、目标和素材可人工编辑，但仍受原始约束，改变约束须重新生成建议。

确认建议时增加资源版本并留下Confirmation。Confirmation.resource_version指确认前的内容版本；确认响应返回的版本是包含确认状态的批准快照，实验生成使用此响应{id,version}。例如内容v2确认后响应v3，确认记录resource_version=2，生成实验必须传v3；两版内容相同。后续编辑为v4 pending，不使旧v3审批自动转移。

实验只能从当前confirmed建议版本生成draft；不新增第七处语言模型调用。单实验采用一个已审核素材、一个本轮推广链接和一种目标指标，形成可解释归因。确认draft时引用的建议仍须为当前confirmed批准版本；建议已改版的旧draft必须取消后重新生成，已经confirmed/running/finished的历史实验保持原批准版本不变。批量确认实验时，每次确认须检查该建议下已有confirmed/running/finished实验的计划预算总和加本次预算<=建议总预算；cancelled但实际已启动的实验也保留其计划预算占用，避免通过取消绕过预算。该约束仅约束系统内计划，不承诺平台实际花费不超限。

计划日期须planned_end_date>=planned_start_date，天数不超过建议批准天数；目标ctr范围0–1，conversion_rate/roas为非负无量纲值，cpa以元计且必须>0。每个实验使用同一个指标口径，不能把百分数3写成点击率0.03的含义。

实验确认、启动、结束都单独校验权限与依赖。启动要求已记录外部计划标识和actual_start_at，不要求接入平台API；系统仅记录人工已执行事实。实际结束时间不得早于开始，实际时间不得在未来；取消已运行实验也必须填写actual_end_at。confirmed/running期间素材不得撤回、链接不得停用。建议内容编辑若已有confirmed/running实验返回409；完成/取消后可新建建议修订，但旧实验不跟随。

## 7. 经营数据与复盘口径

PerformanceRecord只支持日粒度：record_date映射原文period_start=period_end；查询区间两端包含。product_day表示商品整体汇总；experiment_day表示单实验数据。有效业务键分别为(product_id,record_date)和(experiment_id,record_date)，round_id不参与去重，防止同日同一整体数据被复制到两轮。作废记录不占用有效唯一键。

product_day必须experiment_id=null；experiment_day必须提供本商品本轮实验，该实验须已启动（running/finished/已启动后cancelled）。日期须落在实验实际执行的店铺自然日范围，running最迟到当前自然日，不接受未来经营日。素材、方案、链接由后端从实验引用填充，客户端不能任意指定，商品汇总这些字段为null。

impressions、clicks、conversions>=0；第一版conversions定义为“归属支付订单数”，不等同于独立转化人数，允许一次点击产生多个订单。revenue为该统计口径归属支付成交额，spend为广告花费，不混入退款负值或成本。clicks>impressions、conversions>clicks时在汇总warnings及复盘limitations提示人工核对，不静默修正或直接丢弃；复盘必须说明订单计数口径及可能的归因延迟。平台导出的加购、咨询、独立支付人数不能直接当作conversions导入。

- ctr=clicks/impressions，conversion_rate=conversions/clicks，roas=revenue/spend，最多6位小数，Decimal ROUND_HALF_UP。
- cpa=spend/conversions，金额2位小数，ROUND_HALF_UP。
- 分母0返回null，允许0花费收入（自然流量），复盘需说明口径。
- roi保留原文字段名但固定null：当前缺乏完整成本、退款及履约费用，不能以ROAS冒充利润ROI。
- 汇总先合计分子/分母再计算比率；禁止平均CTR和混加product_day与experiment_day。同一复盘只能选一种granularity。

单条录入source只能manual，导入提交时由系统置import，不能冒充导入来源。更正记录增加版本，旧复盘保留生成时record refs及metric_snapshot，不随数据修改而静默变化；需重新生成报告才能反映新数据。已完成轮次不可更正，若需更正应在评审后另加管理员重开流程，本版不预留隐式后门。

生成复盘至少一条有效记录；无数据422 NO_PERFORMANCE_DATA。样本不足可生成带limitations的报告；insights/problem_judgments每条有observed/hypothesis/insufficient和evidence。报告动作有稳定action_id，下一轮从指定报告修订中采纳，完成回到诊断的闭环。

## 8. 导入协议与模板

原文经营导入接口作为统一导入中心的快捷入口，202创建预览任务，不直接写经营数据。处理流程：上传文件→创建批次→轮询到preview_ready→预览/错误行→显式commit→轮询提交结果。校验和提交的轮询使用ImportBatch，不使用GenerationJob；前端必须区分两种202响应。

预览与文件哈希、导入类型、映射、商品/轮次绑定，token有效30分钟。源文件首行为表头，数据从第2行开始，row_number使用原文件行号。重复表头、缺少必填列、未知映射、文件损坏为批次failed；普通字段错误为invalid_rows，批次仍preview_ready。重复行在预览中标记错误，不能靠文件顺序覆盖已存在记录。

allow_partial=true：逐行原子提交，有效行成功、失败行记录commit错误；同批次同文件行号只可成功一次。valid_rows是预览有效行数；succeeded_rows是实际入库数；终态failed_rows=total_rows-succeeded_rows（包含预览无效和提交冲突）。全部成功succeeded、部分partially_succeeded、零成功failed。

allow_partial=false：存在任何预览无效行时拒绝受理409 IMPORT_HAS_ERRORS；无预览错误则202入队，在单事务内全量提交，任一实时冲突整体回滚为failed。业务成功行和批次行状态须同事务写入，崩溃恢复不重复加库存。预览不预留库存、SKU编号或数据唯一键，提交时必须再次校验。

原文要求四类导入；以下给出原始模板列，*表示必填。空白可空列转null，空白可选数组转[]。列表字段用单元格内JSON数组，禁止逗号拆分造成歧义。extra未知列若未映射则报UNKNOWN_COLUMN。

| 模板 | 列与含义 | 唯一性与业务行为 |
|---|---|---|
| products | name*,category*,price*,cost*,target_audience*,selling_points*,product_url,status | selling_points为JSON字符串数组；只新建商品、不按名字覆盖；文件内完全相同业务行判重；商品status只允许draft，首次原图/SKU补齐后再启用 |
| sku-inventory | product_id*,sku_code*,sku_name,spec,price,cost,change_qty*,warning_threshold,location_text,reason_text* | 现有sku_code只能属于product_id；既有SKU只调整库存与显式阈值/库位，传sku_name/spec/price/cost会报SKU_EDIT_NOT_SUPPORTED；新SKU须补齐这些字段，默认active；change_qty为非0增量，结果不得负数；同文件同SKU最多一行 |
| performance-records | record_date*,experiment_id,impressions*,clicks*,conversions*,spend*,revenue*,notes | product_id/round_id/granularity由批次上下文提供；experiment_day时experiment_id必填，product_day必须空；不接受CTR/ROI等计算列 |
| platform-mappings | product_id*,platform*,platform_product_id*,sku_id,platform_sku_id | 只新增映射，SKU关联须成对且属于商品；平台外部标识冲突报错，不隐式更新 |

spec为JSON数组，例如`[{"name":"颜色","value":"白色"}]`，不是自由对象。平台字段映射导入指建立商品/SKU的外部平台标识；CSV表头到业务字段的映射另外用column_mappings明确。错误行不返回整份敏感原始数据，返回字段、行号、代码和原因。

## 11. 前后端联调顺序与验收场景

《联调示例.http》提供带变量的业务请求顺序，执行时需先有部署实例和初始化管理员。示例是契约用例，不代表实际服务测试结果；图片/视频供应商配置需项目接入时填写。

1. 管理员登录，创建唯一店铺、运营和查看人员。再次创建店铺409；查看人员POST商品403。
2. 上传商品原图，建商品/SKU；库存调整相同幂等键重复执行不重复加库存；旧If-Match返回412且无新流水。
3. 录入竞品，创建解析任务201，再run返回202；读取结果后人工采纳。不能访问内网URL。
4. 启用商品、建轮次、生成诊断，轮询到succeeded，读结果并选定{id,version}。
5. 分别生成至少3个主图、脚本和标题方案，选中一个；同类型自动取消旧选择必须原子处理。
6. 媒体任务成功后才出现待审素材；测试失败、超时、重试、取消及迟到结果不发布。未审核素材用于建议应422。
7. 审核通过、创建链接、生成投放建议；运营确认后生成实验草案，再确认实验；未确认直接running为409。
8. 系统仅记录人工平台执行：running须外部标识/开始时间；无任何平台扣费或自动预算修改接口。
9. 同一实验同日重复数据409；product_day与experiment_day不能混合汇总；0分母指标为null。
10. 导入预览不得产生业务记录；部分成功明确成功/失败数量和原文件行号；重复提交不重复写库存或经营数据。
11. 复盘固化数据修订；数据更正后旧报告不变，重新生成新报告。结束实验、完成轮次，再用指定复盘动作创建第二轮。
12. 空环境演示初始化跑通两轮；已有店铺环境初始化演示409。真实模式缺供应商配置不能悄悄返回demo媒体。

## 12. 文件与适用范围

- `openapi.yaml` / `openapi.json`：同一契约的两种序列化，可导入支持OpenAPI 3.1的API工具。
- `数据结构字典.md`：请求与响应Schema、字段必填、类型、枚举和约束；含路径/查询参数表。
- `联调示例.http`：React/FastAPI联调请求顺序，使用占位变量和动态结果变量。
- `契约校验报告.md`：静态OpenAPI校验、原文覆盖率、引用及示例校验结果；不是运行服务验收。

OpenAPI采用3.1.0以提供JSON Schema 2020-12类型与组合表达，不依赖最新版本特性。标准依据：[OpenAPI 3.1.0 官方规范](https://spec.openapis.org/oas/v3.1.0.html)。业务约束为项目设计，不声称来源于该标准。
